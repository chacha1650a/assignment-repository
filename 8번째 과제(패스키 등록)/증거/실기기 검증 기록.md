#### 지운 패스키가 막히는 방식 (T08-C45) — 예상과 다르게 막혔습니다

지운 패스키로 로그인해 보려 했더니, **아이폰이 그 패스키를 후보로 내놓지도 않았습니다.**
시스템 시트에 **"이 웹사이트 또는 앱에 대해 저장된 패스키가 없습니다"** 가 떴습니다.

이유는 서버가 로그인 질문을 내려줄 때 **`allowCredentials`(아직 서버가 인정하는 패스키 목록)** 를 같이 보내기 때문입니다
(`passkey-backend/server.js` 의 `/api/passkey/login/options`). 지운 패스키는 그 목록에서 빠지므로,
**브라우저·운영체제 단계에서 이미 걸러져 요청조차 만들어지지 않습니다.**

즉 막는 층이 두 겹입니다.

| 층 | 무엇이 막는가 | 실기기에서 본 것 |
| --- | --- | --- |
| 1층 (기기) | 서버가 준 `allowCredentials` 에 없으므로 아이폰이 후보로 안 보여줌 | "저장된 패스키가 없습니다" 시트 |
| 2층 (서버) | 그래도 그 패스키로 요청을 만들어 보내면 **401 `unknown_credential`** | 브라우저 UI 를 우회해서 직접 쏴 본 [`배포 서버 검증 기록.md`](배포%20서버%20검증%20기록.md) 의 해당 항목 |

**기기에는 개인키가 그대로 남아 있는데도 들어갈 수 없습니다.** 서버에 짝이 되는 공개키가 없어졌기 때문입니다.

## 확인하면서 찾아낸 것

> 실제로 눌러 보다 발견한 문제와 고친 내용을 여기 적습니다. 없으면 "없었습니다"라고 적습니다.

### 1. 윈도우 PC에서는 패스키를 아예 만들 수 없었습니다 (코드 문제가 아니었음)

처음에는 윈도우 PC의 크롬에서 등록하려 했는데, **"패스키 새로 만들기"를 누를 때마다
"USB 보안 키를 삽입하세요" 화면만 반복해서 떴고, 다른 선택지가 하나도 없었습니다.**

원인을 이렇게 좁혔습니다.

| 확인한 것 | 결과 |
| --- | --- |
| 서버가 `authenticatorAttachment` 로 기기 종류를 강요하는가 | **아니오.** `passkey-backend/server.js` 는 `residentKey: 'preferred'`, `userVerification: 'preferred'` 만 요청하고 기기 종류는 지정하지 않습니다. 플랫폼/보안키 둘 다 허용입니다 |
| 윈도우 설정 → 계정 → 패스키 | **"이 장치에서 암호 키를 사용하려면 Windows Hello PIN을 설정해야 합니다"** 경고가 떠 있었음 |
| 윈도우 설정 → 로그인 옵션 | 얼굴 인식·지문 인식·**PIN 모두 "이 옵션은 현재 사용할 수 없습니다"** — 이 PC에서는 Windows Hello 자체가 막혀 있었음 |
| QR 코드로 휴대폰 연결(하이브리드) 옵션 | 목록에 **나타나지 않음.** 이 방식은 PC가 Bluetooth 로 폰을 찾는 구조라, Bluetooth 가 없거나 꺼져 있으면 선택지 자체가 안 생깁니다 |

즉 **이 PC에는 패스키를 담을 곳(Windows Hello)도, 폰을 빌려 쓸 통로(Bluetooth)도 없어서**
브라우저가 내줄 수 있는 선택지가 USB 보안 키 하나뿐이었던 것입니다. 물리 보안 키는 가지고 있지 않았습니다.

**웹 쪽 코드 문제가 아니었습니다.** 같은 페이지를 아이폰 사파리로 열자 곧바로 정상적으로 등록됐습니다.
이것 자체가 패스키의 성질을 보여주는 기록이라 지우지 않고 남겨 둡니다 —
**패스키는 "기기가 열쇠를 담을 수 있어야" 쓸 수 있고, 그래서 기기를 잃었을 때의 대비(카드 4)가 필요합니다.**

### 2. 같은 비밀번호 관리자에 두 번째 패스키를 만들면 첫 번째가 대체된다 — **가장 큰 발견**

7단계까지 마친 뒤, 남은 패스키 `Daehoon` 으로 다시 들어가려 했더니
**"등록된 적 없는 패스키예요"** (401 `unknown_credential`) 로 거절당했습니다. 서버 상태를 직접 확인해 봤습니다.

```
POST /api/passkey/login/options   {"handle":"daehoon"}
→ 서버가 아직 인정하는 패스키: 1개
   [1] credentialId = DE5n1hnpmbtf8vWh-4hlYPyh...   (= 목록에 남아 있던 "Daehoon")
```

그런데 **아이폰에는 그 개인키가 없었습니다.** 비밀번호 관리자에 남아 있던 것은 이미 지운 쪽(`2번째 Daehoon`)이었습니다.

| | 서버가 아는 것 | 아이폰이 가진 것 |
| --- | --- | --- |
| 패스키 1 `Daehoon` (`DE5n1…`) | ✅ 있음 | ❌ **대체되어 사라짐** |
| 패스키 2 `2번째 Daehoon` (`N0sFG…`) | ❌ 지웠음 | ✅ 개인키 남아 있음 |

**원인.** 비밀번호 관리자는 패스키를 **(사이트 + 사용자 식별자)** 한 쌍으로 묶어 보관합니다.
서버는 같은 계정에 패스키를 더 붙일 때 **같은 사용자 식별자(`users.webauthn_id`)** 를 씁니다 —
그게 표준이고, 그래야 같은 사람으로 인식되기 때문입니다(`server.js` 의 `register/options`).
그래서 같은 관리자에 두 번째를 만드는 순간, 관리자 입장에서는 "같은 사이트의 같은 사용자"라
**먼저 있던 것을 조용히 대체**해 버립니다.

결과적으로 **서버는 패스키 2개를 들고 있는데 실제로 쓸 수 있는 것은 1개**인 상태가 되고,
하필 그 "쓸 수 있는 쪽"을 지우면 **계정에 영영 못 들어갑니다.** `daehoon` 계정이 실제로 그렇게 잠겼습니다.

**왜 자동 검증으로는 못 잡았나.** 가상 인증기(`virtual-authenticator.js`)는 요청할 때마다
새 열쇠 쌍을 만들 뿐, 진짜 비밀번호 관리자처럼 "같은 사용자면 대체" 하는 동작을 하지 않습니다.
그래서 자동 기록에서는 패스키 2개가 끝까지 멀쩡히 동작합니다. **실기기로 눌러 봐야만 나오는 문제였습니다.**

**고친 것.** 서버 동작은 표준대로 두고(사용자 식별자를 계정마다 하나로 유지하는 것이 맞습니다),
화면에서 미리 막기로 했습니다.

- 패스키 목록 옆에 호박색 경고를 상시 표시 — "두 번째 패스키는 반드시 다른 기기나 다른 비밀번호 관리자에 만드세요"
  (`index.html` 의 `.col-warn-replace`)
- **"이 기기의 패스키 추가 등록"** 을 누르면 먼저 확인 창을 띄워 같은 내용을 알림 (`passkey.js` 의 해당 클릭 핸들러)

남은 한계는 제출문 ⑥ 에 적었습니다 — **화면이 경고할 수는 있어도, 사용자가 어느 관리자를 골랐는지 서버는 알 수 없습니다.**
