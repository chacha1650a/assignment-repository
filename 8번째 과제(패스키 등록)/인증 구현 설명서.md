## 넣어 둔 내용에 대하여 (T08-C12)

비공개 서랍에 들어 있는 항목은 **전부 지어낸 것**입니다.
"준비 중인 프로젝트 메모 / 지원하려는 곳 목록 / 이번 주 회고" 세 가지가 기본으로 들어가고, 화면에서 더 넣을 수 있습니다 (T08-C14).
**실제 연락처, 신분증 번호, 실제 지원 내역 같은 진짜 개인정보는 한 건도 넣지 않았습니다.**
심사하시는 분은 공개 소개 페이지까지만 보시면 되고, 잠긴 자리는 열지 않으셔도 됩니다.

## ① 무엇으로 붙였나

**직접 구현 + 널리 쓰이는 라이브러리** 를 섞었습니다. 인증 서비스(Firebase Authentication, Auth0 등)는 쓰지 않았습니다. (T08-C48)

| 맡긴 일 | 무엇으로 | 이름과 버전 |
| --- | --- | --- |
| 패스키 등록·로그인 응답 검증 (CBOR 해석, COSE 공개키 읽기, 서명 확인, origin·RP ID 확인) | **라이브러리** | **@simplewebauthn/server 14.0.1** |
| 일회용 질문(challenge)을 만들고 **한 번만 쓰이게 관리** | **직접 구현** | `challenges` 테이블 + `saveChallenge()` / `consumeChallenge()` (`passkey-backend/server.js:122,132`) |
| 사람을 알아보기 (로그인 상태 유지) | **직접 구현** — 서버에 저장하는 **세션 토큰** | `node:crypto` 의 `randomBytes(32)` + `HMAC-SHA256` (`server.js:102,106`) |
| 브라우저 쪽 WebAuthn 호출과 base64url 변환 | **직접 구현** | [`passkey.js`](passkey.js) — 브라우저용 라이브러리(@simplewebauthn/browser)를 쓰지 않고 `navigator.credentials` 를 직접 부릅니다 |
| 웹 서버 | 라이브러리 | **express 4.21.2** |
| 브라우저에서 다른 주소로 부르기 | 라이브러리 | **cors 2.8.5** |
| 환경변수 읽기 | 라이브러리 | **dotenv 16.4.5** |
| 데이터베이스 | Node 내장 | **`node:sqlite`** (Node 22.13+ 내장, 별도 설치·빌드 없음) |

**로그인 뒤 사람을 알아보는 방식: 세션(서버에 저장하는 토큰)** 입니다. JWT 가 아닙니다. (T08-C32)

- 서명 확인에 성공하면 서버가 256비트 난수 토큰을 만들어 브라우저에 **한 번** 건네줍니다.
- 서버는 토큰 **원문을 저장하지 않고**, `HMAC-SHA256(토큰, SESSION_SECRET)` 값만 `sessions` 테이블에 둡니다.
- 브라우저는 그 뒤 모든 요청에 `Authorization: Bearer <토큰>` 헤더를 붙입니다. **주소(URL)에는 절대 싣지 않습니다.**
- 화면에서는 `sessionStorage` 에 둡니다 — 탭을 닫으면 사라지고, 다른 사이트는 읽을 수 없습니다.
- 토큰에는 **만료 시각(발급으로부터 12시간)** 이 있고, 로그아웃하면 서버가 `revoked_at` 을 찍어 **즉시** 끊습니다.

### 패스키를 저장한 곳 (T08-C26)

패스키의 개인키가 어디에 놓이는지는 **서버가 정하지 않습니다.** 사용자가 등록할 때 브라우저 창에서 고릅니다.
서버는 `residentKey: 'preferred'`, `userVerification: 'preferred'` 만 요청하고 종류를 강요하지 않습니다(`server.js:254`).
실제로 등록한 두 개가 각각 어디에 저장됐는지는 [`증거/실기기 검증 기록.md`](증거/실기기%20검증%20기록.md) 에 적어 두었고,
화면의 패스키 목록에도 **"기기 밖 동기화됨(예: 구글 비밀번호 관리자·iCloud 키체인)" / "이 기기 안"** 으로 표시됩니다
(등록 응답의 `credentialBackedUp` 값을 그대로 보여 줍니다).

## ② 왜 그걸 골랐나

### 검증은 왜 직접 짜지 않고 @simplewebauthn/server 를 골랐나

패스키 응답을 확인하는 일은 겉보기보다 갈래가 많습니다.
CBOR 로 감싼 `attestationObject` 를 풀고, 그 안의 `authenticatorData` 에서 **RP ID 해시**·**플래그**·**서명 횟수**를 끊어 읽고,
COSE 로 적힌 공개키를 알고리즘별로 해석하고, `clientDataJSON` 의 **type·challenge·origin** 을 각각 맞춰 보고,
그 다음에야 서명을 검증합니다. 이 중 **하나만 빼먹어도 "서명이 늘 통과하는" 서버**가 됩니다.

7번 과제에서 비밀번호 해시를 직접 만들지 않고 검증된 bcryptjs 를 쓴 것과 같은 이유입니다.
**틀리면 조용히 뚫리는 자리**는 이미 여러 사람이 들여다본 구현에 맡기는 편이 낫다고 판단했습니다.

### 그런데 질문(challenge) 관리는 왜 직접 짰나

라이브러리는 `expectedChallenge` 를 받기만 하고, **그 값을 어디에 두고 언제 버릴지는 서버가 정해야 합니다.**
그리고 이 과제의 핵심("매번 새 질문이 오고, 이미 쓴 질문은 다시 통하지 않는다")이 정확히 그 자리에 있습니다.
그래서 `challenges` 테이블에 넣어 두고, 확인하는 순간 `used_at` 을 찍어 소모하는 방식으로 직접 만들었습니다(`server.js:132`).
질문을 **화면이 들고 있게 두지 않은 것**도 같은 이유입니다 — 화면이 들고 있으면 화면이 지어낸 질문도 통과합니다.
지어낸 질문을 보내면 어떻게 되는지는 자동 검증 기록의 재사용·위조 항목에 그대로 남아 있습니다.

### 브라우저 쪽은 왜 라이브러리를 안 썼나

브라우저가 할 일은 `navigator.credentials.create()/get()` 을 부르고 결과를 base64url 로 바꿔 보내는 것뿐입니다(약 30줄).
GitHub Pages 에 올리는 정적 페이지라서 **의존성 하나 없이 두는 편**이 배포도 단순하고, 무엇이 오가는지도 눈에 보입니다.

### 세션은 왜 JWT 가 아니라 서버 저장 토큰인가

**로그아웃을 진짜로 끊기 위해서**입니다.
JWT 는 서버가 따로 목록을 들고 있지 않는 한, 한 번 발급하면 만료 전까지 되돌릴 수 없습니다.
이 과제에는 "로그아웃한 뒤 같은 값으로 다시 요청했을 때 거절된다"(T08-C33)를 보여야 하는 자리가 있고,
그것을 **말이 아니라 응답으로** 보이려면 서버가 세션을 들고 있어야 했습니다.

### 저장소는 왜 SQLite 인가

7번 과제와 같은 `node:sqlite` 입니다. Node 22.13+ 에 내장이라 별도 설치·네이티브 빌드가 없고, 배포가 단순합니다.
다만 Render 무료 플랜은 디스크가 영구 저장이 아니라 **다시 배포하면 초기화**됩니다. 이 한계는 ⑥에 적었습니다.

## ④ 안 열리는 것을 확인한 기록

네 가지를 모두 확인했고, **성공한 요청과 거절된 요청을 나란히** 두었습니다. (T08-C50)
아래 표는 로컬 임시 서버 기록 기준이고, **같은 시나리오를 실제 배포본(`https://daehoon-passkey-backend.onrender.com`)에 대고 한 번 더 돌린 결과**가
[`증거/배포 서버 검증 기록.md`](증거/배포%20서버%20검증%20기록.md) 에 있습니다 (27개 확인 모두 통과). 실제 기기·실제 브라우저로 한 확인은
[`증거/실기기 검증 기록.md`](증거/실기기%20검증%20기록.md) 에 있습니다.

### 확인 1 — 로그인 없이 열기

| | 요청 | 응답 |
| --- | --- | --- |
| **거절** | `GET /api/private/items` (토큰 없음) | **401** `{"error":"unauthorized","message":"패스키로 들어와야 볼 수 있어요."}` (T08-C16·C17) |
| **거절** | `GET /api/private/items` + 지어낸 토큰 | **401** `unauthorized` |
| **성공** | `GET /api/private/items` + 패스키로 받은 토큰 | **200** `{"owner":"daehoon-a","count":4,"items":[…]}` |

### 확인 2 — 남의 패스키로 열기

| | 요청 | 응답 |
| --- | --- | --- |
| **거절** | `POST /api/passkey/login/verify` — 계정 A의 credentialId 는 그대로, **서명만 다른 개인키로** | **401** `bad_signature` (T08-C30) |
| **거절** | `GET /api/private/items?handle=tester-b&userId=…` + `X-User-Handle: tester-b` — **A의 토큰** | **200이지만 `owner: "daehoon-a"`** — A 자신의 자료만 (T08-C37·C40) |
| **거절** | 반대 방향: `?handle=daehoon-a` + `X-User-Handle: daehoon-a` — **B의 토큰** | **200이지만 `owner: "tester-b"`** (T08-C38) |
| **거절** | `DELETE /api/private/items/{B의 항목}` — A의 토큰 | **404** `not_found` |
| **거절** | `DELETE /api/passkeys/{B의 패스키}` — A의 토큰 | **404** `not_found` |
| **성공** | 각자 자기 토큰으로 자기 자료 조회 | **200**, A 4건 / B 4건, 내용이 서로 다름 (T08-C36) |

**거절 앞뒤로 상대편 자료 건수가 그대로입니다** (T08-C39). 자동 검증 기록에 거절 전·후 건수를 나란히 세어 두었습니다 — A 4건 → 4건, B 4건 → 4건.

### 확인 3 — 이미 쓴 질문 재사용

| | 요청 | 응답 |
| --- | --- | --- |
| **성공** | 새 질문 `ZVx52oIq…` 으로 로그인 | **200**, 토큰 발급 |
| **거절** | **같은 질문**으로 한 번 더 로그인 | **400** `{"error":"challenge_already_used","message":"이미 한 번 쓴 질문이에요."}` (T08-C31) |
| **거절** | 화면이 **지어낸 질문**으로 로그인 | **400** `challenge_unknown` |

질문이 매번 다르다는 것도 3회씩 연속으로 받아 나란히 적어 두었습니다 (등록 T08-C20 / 로그인 T08-C28).

### 확인 4 — 패스키 삭제 뒤 로그인

| | 요청 | 응답 |
| --- | --- | --- |
| **성공** | 패스키 2개 등록 → `GET /api/passkeys` | **200** `count: 2`, 각각 이름·등록일 (T08-C42·C43) |
| **성공** | 두 번째 패스키 삭제 → **남은 첫 번째**로 로그인 | **200**, 토큰 발급 (T08-C44) |
| **거절** | **지운 패스키**로 로그인 (기기에는 개인키가 그대로 남아 있음) | **401** `unknown_credential` (T08-C45) |
| **거절** | 마지막 하나 남은 패스키 삭제 | **409** `last_passkey` (T08-C46) |
| **거절** | 패스키가 0개가 된 계정에 새 패스키 등록 | **403** `account_locked` (T08-C46) |

### 그 밖에

| | 요청 | 응답 |
| --- | --- | --- |
| **성공** | 로그아웃 **전** `GET /api/private/items` | **200** |
| **거절** | 로그아웃 **뒤 같은 토큰으로** 같은 요청 | **401** `unauthorized` (T08-C33) |
| **거절** | 로그인하지 않고 남의 계정에 패스키 추가 등록 | **401** `unauthorized` |
| **거절** | 등록을 중간에 취소 (질문만 받고 확인 안 함) | 화면에 "취소했거나 시간이 지났습니다. 서버에는 아무것도 저장되지 않았습니다." · 서버 저장 **0건** (T08-C25) |

**기록에서 세션 토큰은 앞 8글자만 남기고 가렸습니다** (T08-C34).
**제출물 어디에도 비밀번호를 입력하는 칸이 없습니다** (T08-C35) — `<input type="password">` 가 한 개도 없습니다.

### 저장된 것이 공개키라는 것 (T08-C21·C22·C23)

등록이 끝난 뒤 서버가 저장한 값입니다.

```json
{
  "nickname": "노트북(윈도우 Hello)",
  "credentialId": "apICH-j-vksi…",
  "publicKey": "pQECAyYgASFYIIa6y8drap29…",
  "설명": "이 값은 COSE 형식의 공개키입니다. 비밀번호도, 비밀번호의 해시도 아닙니다."
}
```

이 값으로는 **서명을 확인할 수만 있고, 서명을 만들 수는 없습니다.** 그래서 이 값이 통째로 새어 나가도 남이 내 계정에 들어올 수 없습니다.
비밀번호 해시와 결정적으로 다른 점입니다 — 해시는 새어 나가면 사전 공격의 출발점이 되지만, 공개키는 원래 공개해도 되는 값입니다.

**개인키가 서버로 오지 않는다는 것**은 등록 요청 본문을 그대로 옮겨 확인했습니다.
브라우저가 보낸 것은 `clientDataJSON`(어떤 질문에 답했는지)과 `attestationObject`(새로 만든 공개키)뿐이고,
개인키를 담은 항목은 **이름이 무엇이든 하나도 없습니다.** 전문은 자동 검증 기록에 있습니다.

## ⑤ AI와 나

[`AI 3줄.md`](AI%203줄.md) 에도 같은 내용을 세 줄로 적어 두었습니다. (T08-C53)

### AI에게 맡긴 일

- WebAuthn 표준에서 서버가 반드시 확인해야 하는 항목이 무엇인지 훑기(RP ID 해시·플래그·origin·type·challenge·서명), 그리고 `@simplewebauthn/server` v14 의 바뀐 API(`registrationInfo.credential.*`) 확인.
- `challenges` / `credentials` / `sessions` / `private_items` 네 표의 첫 설계안과, express 라우트의 뼈대 작성.
- **가상 인증기**(`passkey-backend/virtual-authenticator.js`) 작성 — 실제 패스키는 사람이 지문을 눌러야 만들어져서, 같은 확인을 수십 번 자동으로 돌릴 수 없었습니다. 기기가 하는 일(P-256 열쇠 한 쌍 만들기, `authenticatorData` 조립, CBOR 인코딩, 서명)을 표준 그대로 흉내 내는 코드를 맡겼습니다.
- 확인 시나리오를 돌리고 요청·응답을 그대로 마크다운으로 옮기는 스크립트, 그리고 그 안의 토큰 가리기 처리.
- 이 문서와 [`검증 안내서.md`](검증%20안내서.md) 의 초안 정리.

### 내가 직접 판단한 일

- **비밀번호를 쓰지 않는 것이 목적이므로, 비밀번호 재설정이나 이메일 확인 같은 "우회로"를 하나도 만들지 않기로** 정했습니다. 편의는 줄지만, 그 우회로가 있으면 결국 그쪽이 제일 약한 고리가 됩니다.
- **마지막 패스키는 지울 수 없게 막기로** 정했습니다. 지우게 두면 그 계정에 영영 못 들어옵니다. 대신 "먼저 새 패스키를 등록하라"는 문구를 띄웁니다.
- **패스키가 0개가 된 계정은 새 등록도 막기로** 정했습니다. 열어 주면 계정 이름만 아는 사람이 남의 서랍을 가로챌 수 있습니다. 잠긴 채 두는 쪽이 옳다고 봤습니다.
- **질문 관리만은 라이브러리에 맡기지 않고 직접 짜기로** 정했습니다. 이 과제의 핵심이 정확히 그 자리이기 때문입니다.
- **세션을 JWT 가 아니라 서버 저장 토큰으로** 정했습니다. 로그아웃을 진짜로 끊어야 T08-C33 을 응답으로 보일 수 있습니다.
- 비공개 서랍에 넣을 항목을 **전부 지어낸 내용으로** 정하고, 화면에도 "지어낸 것"이라고 못박아 두었습니다.
- 1번 과제의 `style.css` 와 `script.js` 를 **건드리지 않고** 새 파일 두 개만 붙이는 방식으로 정했습니다.

### AI 제안을 따르지 않은 일

1. **"비공개 항목을 HTML에 미리 넣고 로그인 전에는 CSS로 감추자"** 는 첫 초안을 버렸습니다.
   그렇게 하면 화면에서는 안 보여도 **페이지 소스에는 그대로 남아** 개발자 도구만 열면 다 보입니다.
   숨기는 일은 화면이 아니라 서버가 해야 한다고 보고, 비공개 내용은 로그인 뒤 `GET /api/private/items` 로만 내려오게 고쳤습니다.
2. **"등록이 끝나면 곧바로 세션 토큰도 같이 내주자"** 는 제안을 따르지 않았습니다.
   등록은 "이 공개키를 등록한다"까지이고, 들어가는 것은 **로그인 서명을 한 번 더 거쳐야** 한다고 봤습니다.
   그래야 "로그인할 때도 매번 새 질문에 서명한다"가 흐름에서 실제로 일어납니다.
3. **"편의를 위해 계정 이름 없이도 로그인되게 discoverable credential 만 쓰자"** 는 제안은 이번에는 미뤘습니다.
   화면에서 계정 이름을 받는 편이 **계정 A·B를 갈라 서로의 자료가 안 보이는 것을 보이기(T08-C36~C40)** 에 훨씬 분명했습니다.
   대신 `residentKey: 'preferred'` 로 두어, 기기가 지원하면 저절로 discoverable 로 만들어지게는 했습니다.
4. **"실패 이유를 자세히 알려 주자"** 는 제안 중, **계정이 있는지 없는지가 드러나는 문구는 쓰지 않았습니다.**
   패스키가 없는 이름으로 로그인해도 질문은 똑같이 만들어 주고, 확인 단계에서 거절합니다(`server.js:430`).

## ⑥ 아직 못 막은 것

"없습니다"로 적지 않겠습니다. 실제로 남아 있는 것들입니다. (T08-C51)

### 0. 패스키를 두 개 등록해도 **실제로는 하나뿐일 수 있습니다** — 실기기에서 직접 겪은 것

제일 먼저 적습니다. **자동 검증으로는 끝내 안 나왔고, 실제 아이폰으로 눌러 보다 계정 하나가 잠긴 뒤에야 찾은 문제**이기 때문입니다.

비밀번호 관리자(구글 비밀번호 관리자·iCloud 키체인 등)는 패스키를 **(사이트 + 사용자 식별자)** 한 쌍으로 묶어 보관합니다.
그런데 서버는 같은 계정에 패스키를 더 붙일 때 **같은 사용자 식별자**(`users.webauthn_id`)를 씁니다.
표준대로 한 것이고, 그래야 관리자가 두 패스키를 "같은 사람의 것"으로 인식합니다.

문제는 그 다음입니다. **같은 관리자에 두 번째를 만들면, 관리자가 "같은 사이트의 같은 사용자"로 보고 먼저 있던 것을 조용히 대체해 버립니다.**
서버에는 공개키가 두 줄 남아 화면에도 "패스키 2개"로 보이지만, 기기에 실제로 남은 개인키는 하나뿐입니다.
이 상태에서 **하필 쓸 수 있는 쪽을 지우면 그 계정에는 영영 들어갈 수 없습니다.**

실제로 그렇게 됐습니다. `daehoon` 계정은 지금 서버에 공개키가 1개(`DE5n1hnpmbtf…`) 남아 있는데,
아이폰에는 그 짝이 되는 개인키가 없어서 **들어갈 수 없는 상태**입니다.
요청·응답과 확인 과정은 [`증거/실기기 검증 기록.md`](증거/실기기%20검증%20기록.md) 의 "확인하면서 찾아낸 것 2" 에 그대로 적었습니다.

**지금 해 둔 것** — 서버 동작은 표준대로 두고(사용자 식별자를 계정마다 하나로 유지하는 편이 맞습니다), 화면에서 미리 알리도록 고쳤습니다.

- 패스키 목록 옆에 상시 경고: "두 번째 패스키는 반드시 다른 기기나 다른 비밀번호 관리자에 만드세요" (`index.html` 의 `.col-warn-replace`)
- "이 기기의 패스키 추가 등록" 을 누르면 같은 내용을 확인 창으로 한 번 더 띄움 (`passkey.js`)

**그래도 못 막는 것** — **사용자가 어느 관리자를 골랐는지 서버는 알 수 없습니다.**
등록 응답에는 "기기 밖으로 동기화되는가"(`credentialBackedUp`) 정도만 담기고, 어느 관리자인지는 오지 않습니다.
그래서 서버는 "방금 그 두 번째가 첫 번째를 덮어썼다"를 감지할 방법이 없고, 화면의 경고에 기댈 수밖에 없습니다.
제대로 막으려면 **마지막 하나를 지울 때가 아니라, 남은 패스키로 실제 로그인이 되는지 확인한 뒤에야 삭제를 허용**하는 식이 되어야 합니다.
(예: 지우기 전에 "남길 패스키로 지금 한 번 로그인해 보세요" 를 요구하기)

### 1. 계정 이름을 먼저 차지하는 것을 막지 못합니다 — 가장 큰 구멍

패스키만으로 잠그다 보니 **"처음 등록하는 사람이 그 이름의 주인"** 이 되는 구조입니다(`server.js:254`, 계정이 없으면 세션 없이도 질문을 내줌).
그래서 남이 먼저 `daehoon-a` 라는 이름으로 자기 패스키를 등록해 버리면, 저는 그 이름을 다시 쓸 수 없습니다.
서랍 안의 내용이 새어 나가지는 않지만(각 계정은 각자의 서랍만 봅니다), **이름을 선점당하는 것 자체는 막지 못합니다.**
제대로 막으려면 초대 코드나 이메일 확인 같은 "이 이름이 정말 당신 것인가"를 확인하는 절차가 하나 더 필요합니다.
이번 과제에서는 비밀번호 없는 흐름 자체에 집중하려고 넣지 않았습니다.

### 2. 세션 토큰을 훔쳐 가면 그 토큰이 만료될 때까지 통합니다

패스키는 **로그인하는 순간**을 안전하게 만들지만, 그 뒤 12시간 동안 사람을 알아보는 것은 여전히 토큰입니다.
이 페이지에 XSS 구멍이 생기면 그 토큰을 읽어 갈 수 있습니다(`sessionStorage` 에 두기 때문에).
지금 막아 둔 것은 여기까지입니다 — 화면에 넣는 값을 전부 `escapeHtml()` 로 감싸고(`passkey.js:125`), 토큰을 URL 에 싣지 않고, 만료를 12시간으로 두고, 로그아웃을 서버에서 끊습니다.
못 막은 것은 **토큰 자체를 기기에 묶는 일**입니다. 토큰을 `HttpOnly` 쿠키로 옮기거나, 요청마다 패스키로 다시 서명하게 하면 줄일 수 있습니다.

### 3. 질문을 120초나 들고 있습니다

`CHALLENGE_TTL_SECONDS = 120` 입니다. 사람이 지문이나 PIN 을 누를 시간을 주려고 넉넉히 잡았는데,
그만큼 **가로챈 질문을 써 볼 수 있는 창이 길다**는 뜻이기도 합니다.
한 번 쓰면 즉시 소모되니 재사용은 막히지만, 시간 자체는 더 줄일 수 있습니다.

### 4. 서명 횟수(counter)를 저장만 하고, 거꾸로 가도 막지 않습니다

`server.js:518` 에서 새 counter 를 저장은 하는데, **이전보다 작아졌을 때 거절하지는 않습니다.**
원래 이 값은 "패스키가 복제됐다"를 눈치채는 데 쓰라고 있는 값입니다.
막지 않은 이유는, 요즘 클라우드로 동기화되는 패스키(구글 비밀번호 관리자·iCloud 키체인)는 대부분 counter 를 **0으로 고정**해서 보내
검사를 켜면 정상 로그인이 거절되기 때문입니다. 다만 **"그래서 안 켰다"는 것과 "그래서 복제를 못 잡는다"는 것은 다른 말**이고, 지금은 못 잡습니다.

### 5. 요청 횟수를 제한하지 않습니다

`/api/passkey/login/options` 를 초당 수백 번 부르면 그만큼 질문 줄이 쌓입니다.
로그인 자체가 뚫리지는 않지만(서명이 있어야 하므로), **서버를 지치게 만드는 것은 막지 못합니다.**
5분마다 오래된 질문을 지우는 청소(`server.js:159`)만 있고, 요청 수 제한은 없습니다.

### 6. 다시 배포하면 등록한 패스키가 사라집니다

Render 무료 플랜은 디스크가 영구 저장이 아니라 **재배포 때 `passkey.db` 가 초기화**됩니다.
그러면 기기에는 개인키가 남아 있는데 서버에 짝이 되는 공개키가 없어져, **아무도 못 들어오는 상태**가 됩니다(새 이름으로 다시 등록해야 합니다).
안전 쪽으로 틀린 것이긴 하지만, 실제 서비스라면 그대로 두면 안 되는 문제입니다. 유료 디스크나 관리형 DB로 옮겨야 합니다.

### 7. 등록할 때 기기가 어떤 것인지 확인하지 않습니다

`attestationType: 'none'` 으로 두어 **증명서를 받지 않습니다.** 그래서 "이 패스키가 정말 그 회사의 보안 키에서 나왔는가"를 확인하지 못합니다.
개인 포트폴리오에는 필요 없다고 봤지만, 회사에서 기기를 통제해야 하는 곳이라면 이 자리를 채워야 합니다.
