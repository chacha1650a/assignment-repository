# AI와 내 판단 3줄

**1줄 (AI에게 맡긴 일)**: 패스키 백엔드(`passkey-backend/server.js`)의 뼈대 — `challenges`·`credentials`·`sessions`·`private_items` 네 표의 첫 설계, `@simplewebauthn/server` v14 로 등록·로그인 응답을 검증하는 라우트, 세션 토큰 발급·취소, 주인 확인(`requireAuth`) — 과, 1번 과제 소개 페이지에 덧붙일 비공개 섹션 마크업(`index.html`)·`passkey.css`·`passkey.js` 를 맡겼습니다. WebAuthn 에서 서버가 반드시 확인해야 하는 항목(RP ID 해시·플래그·origin·type·challenge·서명)을 표준에서 훑어 정리하는 일도 맡겼습니다. 그리고 무엇보다 **가상 인증기**(`passkey-backend/virtual-authenticator.js`) 를 만들게 했습니다 — 실제 패스키는 사람이 지문을 눌러야 만들어져서 "이미 쓴 질문은 정말 막히나"를 수십 번 자동으로 돌려 볼 수 없기 때문에, 기기가 하는 일(P-256 열쇠 한 쌍 만들기, `authenticatorData` 조립, CBOR 인코딩, 서명)을 표준 그대로 흉내 내게 하고, 그것으로 **실제 요청을 보내 응답을 그대로 받아 적는** 스크립트를 짜게 했습니다. 그래야 제출한 요청·응답이 제가 지어낸 것이 아니라 진짜 서버가 답한 것이 됩니다.

**2줄 (내가 직접 판단한 일)**: ① **비밀번호 재설정이나 이메일 확인 같은 우회로를 하나도 만들지 않기로** 한 것 — 비밀번호를 없애는 것이 이 과제의 목적인데, 우회로를 두면 결국 그쪽이 제일 약한 고리가 되어 패스키를 붙인 의미가 사라집니다. ② **마지막 패스키는 지울 수 없게 막고(409), 어쩌다 패스키가 0개가 된 계정은 새 등록도 막기로(403)** 한 것 — 열어 주면 계정 이름만 아는 사람이 남의 서랍을 가로챌 수 있어서, 잠긴 채 두는 쪽이 옳다고 봤습니다. ③ **질문(challenge) 관리만은 라이브러리에 맡기지 않고 직접 짜기로** 한 것 — 이 과제의 핵심이 정확히 그 자리이고, 라이브러리는 "질문을 어디에 두고 언제 버릴지"는 정해 주지 않습니다. ④ **세션을 JWT 가 아니라 서버 저장 토큰으로** 한 것 — 로그아웃을 진짜로 끊어야 "로그아웃 뒤 같은 값으로 요청하면 거절된다"를 말이 아니라 응답으로 보일 수 있습니다. ⑤ 1번 과제의 `style.css`·`script.js` 를 **한 줄도 고치지 않고** 새 파일 두 개만 붙이는 방식으로 정한 것 — 1번 제출물이 지금도 그대로 열려야 하기 때문입니다. ⑥ ⑥번 항목(아직 못 막은 것)에 계정 이름 선점·토큰 탈취·서명 횟수 미검사·재배포 시 초기화 같은 것들을 감추지 않고 그대로 적기로 한 것.

**3줄 (AI 제안을 따르지 않은 일)**: AI는 첫 초안에서 **비공개 항목을 HTML 에 미리 넣어 두고 로그인 전에는 CSS 로 감추는** 방식을 냈습니다. 화면 전환이 즉각적이고 코드가 단순하다는 이유였습니다. 따르지 않았습니다. 그렇게 하면 화면에서는 안 보여도 **페이지 소스에는 내용이 그대로 남아** 개발자 도구만 열면 다 보입니다. 숨기는 일은 화면이 아니라 서버가 해야 한다고 보고, 비공개 내용은 로그인 뒤 `GET /api/private/items` 로만 내려오게 고쳤습니다(그래서 지금은 로그인 전 페이지 소스에 서랍 내용이 한 글자도 없습니다). 같은 이유로 **"등록이 끝나면 곧바로 세션 토큰도 같이 내주자"** 는 제안도 따르지 않았습니다 — 등록은 "이 공개키를 등록한다"까지이고, 들어가는 것은 로그인 서명을 한 번 더 거쳐야 "로그인할 때도 매번 새 질문에 서명한다"가 흐름에서 실제로 일어나기 때문입니다.
