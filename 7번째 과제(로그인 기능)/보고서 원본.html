맡긴 일무엇으로이름과 버전
비밀번호 되돌릴 수 없게 만들기라이브러리bcryptjs 3.0.3 (알고리즘 bcrypt, 반복 12회)

비밀번호에 bcrypt를 고른 이유

한 문장으로: 비밀번호를 다루는 부분은 직접 만들면 반드시 어딘가 틀리기 때문에, 오래 검증된 표준을 그대로 쓰고 싶었습니다.

  • 계정마다 다른 소금값(salt)을 알아서 붙여 줍니다. 제가 salt를 만들고 붙이고 꺼내는 코드를 짜면 그 자리에서 실수가 납니다.
  • 일부러 느립니다(반복 12회). 훔쳐 간 사람이 빠르게 다 대입해 보는 것을 어렵게 합니다.
  • 비교도 bcrypt.compareSync에 맡겼습니다. 문자열을 ===로 비교하면 걸린 시간으로 정답을 알아내는 공격이 가능한데, 라이브러리가 그 부분까지 처리합니다.
  • bcryptjs는 순수 자바스크립트라 네이티브 빌드가 필요 없어 무료 배포 환경에서 빌드가 깨지지 않습니다.

함께 검토했지만 고르지 않은 것

검토한 것고르지 않은 이유
Firebase Authentication (인증 서비스)가입·로그인은 편해지지만 "남의 자료가 안 열린다"를 만드는 소스가 내 코드에 남지 않아, 이 과제가 요구하는 "어디를 고쳤나 / 무엇이 거절을 만드나"를 보일 수가 없었음
JWT (jsonwebtoken)서명만 맞으면 통과시키는 구조라 로그아웃해도 만료 전까지 그 토큰이 계속 통함. 통과 기준(로그아웃 뒤 거절)을 만들려면 결국 서버에 취소 목록이 필요해, 처음부터 서버 세션이 단순했음
express-session + 쿠키화면은 GitHub Pages, 서버는 Render로 주소가 달라 크로스 사이트 쿠키를 써야 하는데, 요즘 브라우저가 이를 막는 경우가 많아 심사자 환경에서 로그인이 안 될 위험이 컸음
SHA-256 한 번만 걸어 저장빠른 것이 장점인 해시라 오히려 다 대입해 보기 좋음. 비밀번호 보관에는 일부러 느린 함수를 써야 한다고 판단
argon2 / scrypt / PBKDF2argon2는 네이티브 빌드가 필요해 무료 배포에서 자주 깨지고, scrypt·PBKDF2는 salt 생성·저장 형식을 직접 설계해야 해서 "직접 만들지 않는다"는 원칙에서 멀어짐

거절을 만들어 내는 소스 — 핵심 세 곳

// 1) server.js:145 — 로그인 안 했으면 여기서 끝난다
function requireAuth(req, res, next) {
  const token = header.startsWith('Bearer ') ? header.slice(7).trim() : '';
  if (!token) return res.status(401)...
  const row = db.prepare('SELECT * FROM sessions WHERE token_hash = ?').get(hashToken(token));
  if (!row || row.revoked_at) return res.status(401)...      // 로그아웃/비번변경으로 끊긴 토큰
  if (new Date(row.expires_at).getTime() <= Date.now()) return res.status(401)...  // 만료
  req.user = user;   // 주소·헤더·본문에 뭐라고 적혀 있든, 계정은 여기서만 정해진다
}

// 2) server.js:262 — 목록에도 반드시 주인 조건이 붙는다
db.prepare('SELECT * FROM entries WHERE user_id = ? ORDER BY date').all(req.user.id);

// 3) server.js:303 — 한 건을 다룰 때. 주인이 아니면 "없는 것"이 된다
function findOwnEntry(userId, id) {
  return db.prepare('SELECT * FROM entries WHERE id = ? AND user_id = ?').get(Number(id), userId) || null;
}

세 번째가 읽기·수정·삭제 세 경로 모두에서 가장 먼저 호출됩니다 (server.js:309 / 315 / 322). 특히 수정은 주인 확인을 통과한 뒤에야 저장 함수를 부르기 때문에, 거절된 요청은 데이터베이스를 한 글자도 건드리지 않습니다.

화면에서 막은 것이 아닙니다. 화면은 일기 영역을 hidden으로 시작하고 토큰이 있어도 서버에 GET /api/auth/me를 먼저 물어보지만, 이것은 편의일 뿐입니다. 개발자 도구로 appView.hidden = false를 강제로 풀어도 화면은 비어 있습니다 — 데이터가 서버에서 오지 않기 때문입니다.
04

안 열리는 것을 확인한 기록

"막았습니다"라는 문장은 근거가 아니라고 해서, 실제로 요청을 보내 받은 응답을 그대로 옮겼습니다. 아래는 요약이고, 전체 요청·응답은 저장소의 증거/ 폴더에 세 개 파일로 있습니다. 비밀번호는 ********, 토큰은 앞 8글자만 남기고 …생략으로 가렸습니다.

증거 파일무엇을 확인했나
증거/확인 기록.md1차 — 계정 A·B·C로 로컬 서버에서 전 항목 확인(628줄)
증거/테스트 계정 검증 기록.md2차 — 테스트 계정을 새로 만들어 화면까지 눌러 가며 재확인. 이 과정에서 문제를 하나 찾아 고침(5절)
증거/배포 서버 검증 기록.md3차 — 배포된 서버에 같은 확인. 심사자가 밟는 경로(Pages 화면 → Render 서버)까지 브라우저로 확인

확인 1 — 로그인하지 않고 자료를 부르면

GET /api/entries  (토큰 없음)          → 401 {"error":"unauthorized","message":"로그인이 필요해요."}
GET /api/entries  (지어낸 토큰)        → 401 {"error":"unauthorized", ...}
GET /api/entries  (로그인한 토큰)      → 200 내 5일 기록

브라우저에서 index.html#/diary를 직접 쳐도 화면이 서버에 물어보고 위 401을 받아 로그인 화면을 보여줍니다.

확인 2 — 로그아웃 뒤 같은 값으로 다시 요청하면

GET /api/entries  Authorization: Bearer tu3WrPOR…생략   → 200 5일 기록
POST /api/auth/logout  (같은 토큰)                    → 200 {"loggedOut":true}
GET /api/entries  Authorization: Bearer tu3WrPOR…생략   → 401 {"error":"unauthorized"}

주소도 방식도 보낸 토큰도 같고, 달라진 것은 사이에 로그아웃을 했다는 것뿐입니다. 브라우저에서만 지운 것이 아니라 서버의 sessions 행에 revoked_at이 찍힙니다. 비밀번호를 바꿨을 때도 같습니다(변경 전 200 → 변경 후 같은 요청이 401).

확인 3 — 남의 자료 읽기·수정·삭제 (양방향)

방향요청응답
A → B 읽기GET /api/entries/6 (A 토큰)404 그런 기록이 없어요.
A → B 수정PUT /api/entries/6 (A 토큰)404
A → B 삭제DELETE /api/entries/6 (A 토큰)404
주인이 부르면GET /api/entries/6 (B 토큰)200 B의 기록
B → A 읽기 / 수정 / 삭제GET·PUT·DELETE /api/entries/1 (B 토큰)셋 다 404

403이 아니라 404를 쓴 이유: 403은 "있긴 한데 너는 안 돼"라고 알려주는 셈이라 남의 기록 id가 실제로 있다는 사실이 새어 나갑니다. 404는 그것조차 알려주지 않습니다.

거절 앞뒤로 반대편이 그대로인지: A가 B를 건드리기 전 B는 2건, 건드린 뒤에도 2건이었고 응답 JSON을 통째로 비교해도 한 글자도 다르지 않았습니다. 반대 방향도 5건 → 5건, 내용 동일. 새로 생긴 기록도 없습니다.

확인 4 — 주소·헤더·본문에 남의 계정을 적어 보내면

GET /api/entries?userId=2            (A 토큰) → 200 돌아온 id [1,2,3,4,5] = A 것뿐
GET /api/entries  X-User-Id: 2       (A 토큰) → 200 돌아온 id [1,2,3,4,5] = A 것뿐
PUT /api/entries/date/2026-09-06    본문 {"userId":2,"user_id":2,...}
                                        → 200 A의 2026-09-06 으로 저장. B 목록에는 그 날짜 없음

서버는 주소·헤더·본문의 계정 번호를 읽는 코드 자체가 없습니다. 계정은 requireAuth가 토큰에서 정한 req.user.id 하나뿐입니다.

확인 5 — 목록 격리와 비밀번호 보관

같은 주소·같은 방식(GET /api/entries)에 토큰만 바꿔 불렀습니다. A는 [1,2,3,4,5], B는 [6,7] — 겹치는 id 0개.

저장된 비밀번호는 users 테이블을 그대로 열어봤습니다. 두 계정은 똑같은 비밀번호로 만들었습니다.

id=1  email=mochi-a@example.com
password_hash=$2b$12$TaYWqBoF5TXHLWxJHj.2HONopQcwQ6okhZ2XRnudmbjQfbxKBMl8.
id=2  email=mochi-b@example.com
password_hash=$2b$12$WUjpgjt2mZMN5e6wBRVZjOX7x.7xEF2TUnZ7AcwZhP5IsjUWseVO.
  • 입력한 글자는 어디에도 보이지 않습니다.
  • 같은 비밀번호인데 저장값이 서로 다릅니다 — bcrypt가 계정마다 다른 소금값을 붙이기 때문($2b$12$ 뒤 22글자).
  • 서버 로그 전체를 뒤져도 비밀번호 원문은 한 건도 없습니다. 로그에는 시각·방식·경로·상태 코드만 남깁니다(server.js:184).

같은 이메일로 두 번 가입409 email_taken (email_lower UNIQUE)

아직 못 막은 것

다 막았다고 적는 것보다 못 막은 것을 적는 쪽이 정직하다고 해서, 감추지 않고 그대로 적습니다.

못 막은 것왜 위험한가 / 지금 상태
① 무차별 대입 (가장 큰 구멍)로그인 요청 횟수에 아무 제한이 없어 비밀번호를 계속 넣어볼 수 있음. bcrypt 12회가 속도를 크게 늦추긴 하지만 짧거나 흔한 비밀번호면 결국 뚫림. 계정 잠금도 없어 공격이 시작돼도 본인이 알 방법이 없음. 시도 횟수 제한·실패 알림을 넣어야 하는데 시간이 모자랐음
② 비밀번호 재설정 없음잊으면 되찾을 방법이 없음(로그인 상태에서 바꾸는 것만 됨). 급히 붙이다 "이메일만 맞으면 바꿔 준다" 같은 위험한 방식이 되기 쉬운 지점이라 아예 없다고 적어 둠
③ 토큰을 localStorage에 둠XSS가 생기면 그 스크립트가 토큰을 읽어 감. 훔치면 비밀번호를 몰라도 남의 일기를 다 볼 수 있고 만료가 12시간이라 그만큼 피해 창이 열림. 값을 넣을 때 innerHTML 대신 textContent를 쓰도록 정리했지만 이건 예방이지 방어가 아님. HttpOnly 쿠키를 쓰려면 화면·서버 주소가 달라 크로스 사이트 쿠키 문제에 걸림
④ 2단계 인증 없음비밀번호 하나만 맞으면 들어옴. 새 나가면 그걸로 끝
⑤ 접속 기록(감사 로그) 없음누가 로그인에 실패·성공했는지 남지 않음. 누가 내 계정을 두드렸는지, 언제 뚫렸는지 나중에 알 수 없음
⑥ 이메일 확인 절차 없음남의 이메일 주소로도 가입 가능. 지금은 메일을 보내지 않아 피해가 없지만, 비밀번호 재설정을 붙이면 곧바로 문제가 됨
⑦ 무료 배포의 저장 한계
— 실제로 겪음		Render 무료 플랜은 디스크가 영구 저장이 아니라, 15분 넘게 요청이 없어 잠들었다 깨어나면 계정과 일기가 통째로 사라짐. 추측이 아니라 재봤음 — 계정과 5일 기록을 넣고 20분간 요청을 전혀 보내지 않은 뒤 로그인하니 401 invalid_credentials. 재배포도 코드 변경도 없었음. 유료 디스크나 관리형 DB(Neon·Supabase 등)로 옮겨야 하는데 기한 안에 못 함
⑦은 인증이 뚫린 것이 아니라 호스팅의 저장 한계입니다. 가입·로그인은 언제나 되므로, 심사하시는 분이 직접 계정을 만들어 확인하시는 데에는 지장이 없습니다. 제 5일 기록은 이 보고서와 증거 파일에 그대로 남아 있습니다.

구분내용
AI에게 맡긴 일인증 백엔드(server.js) 전체 코드 — 계정·세션·일기 표 설계, bcryptjs 적용, 세션 발급·취소·만료, 주인 확인(requireAuth, findOwnEntry). 6번의 script.js를 서버 호출 방식으로 옮긴 app.js, 로그인 화면 마크업·CSS. 그리고 확인 기록을 손으로 옮겨 적는 대신 실제로 요청을 보내 응답을 그대로 받아 적고 비밀값을 가려 주는 스크립트 — 제출한 요청·응답이 지어낸 것이 아니라 진짜 서버가 답한 것이 되도록 하기 위해서

AI 제안을 따르지 않은 일AI는 처음에 JWT(jsonwebtoken)로 붙이자고 했습니다. 코드가 짧고 서버에 세션 표가 필요 없다는 이유였습니다. 따르지 않았습니다. JWT는 서명만 맞으면 통과시켜 로그아웃해도 만료 전까지 그 토큰이 계속 통하는데, 이 과제의 통과 기준은 "로그아웃 뒤 같은 값으로 요청하면 거절된다"입니다. 그걸 만들려면 어차피 서버에 취소 목록을 둬야 하니, 처음부터 서버 세션이 더 단순하고 정직하다고 판단해 방식을 바꾸게 했습니다
AI가 만든 것을 그대로 믿지 않으려고 검증을 세 번 나눠서 했습니다. 1차(로컬), 2차(테스트 계정을 새로 만들어 화면까지), 3차(배포본). 2차에서 로그아웃 뒤 DOM에 기록이 남는 문제를, 3차 직전에 배포 실패 원인을 찾았습니다(5절). 한 번만 확인하고 넘어갔다면 둘 다 놓쳤을 것입니다.
