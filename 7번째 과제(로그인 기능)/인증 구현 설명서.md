## ① 무엇으로 붙였나

**직접 구현 + 널리 쓰이는 라이브러리** 를 섞었습니다. 인증 서비스(Firebase 등)는 쓰지 않았습니다.

| 맡긴 일 | 무엇으로 | 이름과 버전 |
| --- | --- | --- |
| 비밀번호를 되돌릴 수 없게 바꾸기 | **라이브러리** | **bcryptjs 3.0.3** (알고리즘 **bcrypt**, 반복 12회) |
| 사람을 알아보기 (로그인 상태 유지) | **직접 구현** — 서버에 저장하는 **세션 토큰** | 표준 `node:crypto` 의 `randomBytes(32)` + `HMAC-SHA256` |
| 웹 서버 | 라이브러리 | **express 4.22.2** |
| 브라우저에서 다른 주소로 부르기 | 라이브러리 | **cors 2.8.6** |
| 환경변수 읽기 | 라이브러리 | **dotenv 16.6.1** |
| 데이터베이스 | Node 내장 | **`node:sqlite`** (Node 22+ 내장, 별도 설치·빌드 없음) |

**사람을 알아보는 방식: 세션(서버에 저장하는 토큰)** 입니다.

- 로그인에 성공하면 서버가 256비트 난수 토큰을 만들어 브라우저에 한 번 건네줍니다.
- 서버는 토큰 **원문을 저장하지 않고**, `HMAC-SHA256(토큰, SESSION_SECRET)` 값만 `sessions` 테이블에 둡니다.
- 브라우저는 그 뒤 모든 요청에 `Authorization: Bearer <토큰>` 헤더를 붙입니다. **주소(URL)에는 절대 싣지 않습니다.**
- 토큰에는 **만료 시각(발급으로부터 12시간)** 이 있고, 로그아웃·비밀번호 변경 시 서버가 `revoked_at` 을 찍어 즉시 끊습니다.

## ② 왜 그걸 골랐나

### 비밀번호 — bcrypt(bcryptjs)를 고른 이유

한 문장으로: **비밀번호를 다루는 부분은 직접 만들면 반드시 어딘가 틀리기 때문에, 20년 넘게 검증된 표준 알고리즘을 그대로 쓰고 싶었습니다.**

- bcrypt는 계정마다 다른 **소금값(salt)을 알아서 붙여 줍니다.** 제가 salt를 만들고 붙이고 꺼내는 코드를 짜면 그 자리에서 실수가 납니다.
- **일부러 느립니다(반복 12회).** 비밀번호 하나 확인에 몇십 밀리초가 걸리게 만들어서, 훔쳐 간 사람이 빠르게 다 대입해 보는 것을 어렵게 합니다.
- `bcryptjs` 는 순수 자바스크립트라 **네이티브 빌드가 필요 없습니다.** 무료 배포 환경(Render)에서 빌드가 깨지지 않는 쪽을 골랐습니다.
- 비교도 `bcrypt.compareSync` 에 맡겼습니다. 문자열을 `===` 로 비교하면 걸린 시간으로 정답을 알아내는 공격(타이밍 공격)이 가능한데, 라이브러리가 그 부분까지 처리합니다.

argon2는 더 최신이고 더 좋다는 평이지만 네이티브 빌드가 필요해 무료 배포에서 자주 깨지고, PBKDF2는 직접 반복 횟수·salt 길이를 정해야 해서 제가 판단해야 할 것이 늘어납니다. scrypt는 Node에 내장돼 있어 매력적이었지만 salt 생성과 저장 형식(어디까지가 salt인지)을 제가 직접 설계해야 해서, "직접 만들지 않는다"는 원칙에서 멀어집니다.

### 함께 검토했지만 고르지 않은 방법

| 검토한 것 | 고르지 않은 이유 (한 문장) |
| --- | --- |
| **Firebase Authentication** (인증 서비스) | 가입·로그인은 편해지지만 **"남의 자료가 안 열린다"를 만드는 소스가 제 코드에 남지 않아서**, 이 과제가 요구하는 "어디를 고쳤나 / 무엇이 거절을 만드나"를 보여줄 수가 없었습니다. |
| **JWT (`jsonwebtoken`)** | 서명만 맞으면 통과시키는 구조라 **로그아웃해도 만료 전까지 그 토큰이 계속 통합니다.** "로그아웃 뒤 같은 값으로 요청하면 거절된다"를 만들려면 결국 서버에 취소 목록을 둬야 해서, 처음부터 서버에 세션을 두는 쪽이 단순했습니다. |
| **express-session + 쿠키** | 화면은 GitHub Pages(정적), 서버는 Render로 **주소가 서로 달라** 크로스 사이트 쿠키(`SameSite=None`)를 써야 하는데, 요즘 브라우저가 이런 쿠키를 막는 경우가 많아 심사하시는 분 환경에서 로그인이 안 될 위험이 컸습니다. |
| **비밀번호를 SHA-256 한 번만 걸어 저장** | 빠른 것이 장점인 해시라 오히려 **다 대입해 보기 좋습니다.** 비밀번호 보관에는 일부러 느린 함수를 써야 한다고 판단했습니다. |

### 거절을 만들어 내는 소스 위치 (핵심 3곳)

```js
// 1) mochi-diary-auth-backend/server.js:145 — 로그인 안 했으면 여기서 끝난다
function requireAuth(req, res, next) {
  const header = req.header('Authorization') || '';
  const token = header.startsWith('Bearer ') ? header.slice(7).trim() : '';
  if (!token) return res.status(401).json({ error: 'unauthorized', message: '로그인이 필요해요.' });
  const row = db.prepare('SELECT * FROM sessions WHERE token_hash = ?').get(hashToken(token));
  if (!row || row.revoked_at) return res.status(401).json(...);      // 로그아웃/비번변경으로 끊긴 토큰
  if (new Date(row.expires_at).getTime() <= Date.now()) return res.status(401).json(...);  // 만료
  req.user = user;   // <- 주소·헤더·본문에 뭐라고 적혀 있든, 계정은 여기서만 정해진다
  next();
}

// 2) server.js:262 — 목록에도 반드시 주인 조건이 붙는다
db.prepare('SELECT * FROM entries WHERE user_id = ? ORDER BY date').all(req.user.id);

// 3) server.js:303 — 한 건을 다룰 때. 주인이 아니면 "없는 것"이 된다
function findOwnEntry(userId, id) {
  return db.prepare('SELECT * FROM entries WHERE id = ? AND user_id = ?').get(Number(id), userId) || null;
}
```

세 번째가 **읽기·수정·삭제 세 경로 모두에서 가장 먼저 호출**됩니다(`server.js:309`, `315`, `322`).
특히 수정(`PUT`)은 **주인 확인을 통과한 뒤에야 저장 함수를 부르기 때문에**, 거절된 요청은 데이터베이스를 한 글자도 건드리지 않습니다.

### 화면 쪽에서 막은 것이 아니라는 점

화면은 `index.html` 에서 일기 영역을 `hidden` 으로 시작하고, 토큰이 있어도 **서버에 `GET /api/auth/me` 를 먼저 물어봐서 통과할 때만** 일기 화면을 엽니다(`app.js:899`).
하지만 이것은 편의일 뿐이고, **진짜 잠금은 전부 서버(`requireAuth`)에 있습니다.** 브라우저 개발자 도구로 `appView.hidden = false` 를 강제로 풀어도 화면은 비어 있습니다 — 데이터가 서버에서 오지 않기 때문입니다.

배포까지 마친 뒤에는 **실제 배포 서버(`https://mochi-diary-auth-backend.onrender.com`)에 같은 확인을 한 번 더** 했고,
그 요청·응답은 [`증거/배포 서버 검증 기록.md`](증거/배포%20서버%20검증%20기록.md) 에 있습니다.

확인에 쓴 계정: **계정 A**(`mochi-a@example.com`, 5일 기록이 든 계정), **계정 B**(`mochi-b@example.com`, A와 **일부러 같은 비밀번호**로 만듦), **계정 C**(계정 삭제 확인용 일회용). 비밀번호는 적지 않습니다.

### 확인 1 — 로그인하지 않고 자료 화면을 열면

| | 요청 | 응답 |
| --- | --- | --- |
| 거절 | `GET /api/entries` (토큰 없음) | `401 {"error":"unauthorized","message":"로그인이 필요해요."}` |
| 거절 | `GET /api/entries` (지어낸 토큰) | `401 {"error":"unauthorized",...}` |
| 성공 | `GET /api/entries` (로그인한 A의 토큰) | `200` — A의 5일 기록 |

브라우저에서 `index.html#/diary` 를 직접 쳐서 들어가도, 화면이 서버에 물어보고 위 401을 받아 **로그인 화면**을 보여줍니다.

### 확인 2 — 로그아웃 뒤 같은 값으로 다시 요청하면

| | 요청 | 응답 |
| --- | --- | --- |
| 성공 | `GET /api/entries` + `Authorization: Bearer tu3WrPOR…생략` | `200` — 5일 기록 |
| (사이) | `POST /api/auth/logout` (같은 토큰) | `200 {"loggedOut":true}` |
| 거절 | `GET /api/entries` + **완전히 같은** `Bearer tu3WrPOR…생략` | `401 {"error":"unauthorized","message":"로그인이 필요해요."}` |

주소도 방식도 보낸 토큰도 같고, **달라진 것은 사이에 로그아웃을 했다는 것뿐**입니다.
브라우저에서만 지운 것이 아니라 서버의 `sessions` 행에 `revoked_at` 이 찍힙니다.

비밀번호를 바꿨을 때도 같습니다 — 계정 B의 토큰이 변경 전에는 `200`, 변경 뒤에는 같은 요청이 `401` 이 됩니다.

### 확인 3 — 남의 자료 읽기 · 수정 · 삭제 (양방향)

계정 A의 기록 id = 1~5, 계정 B의 기록 id = 6, 7 입니다.

| 방향 | 요청 | 응답 |
| --- | --- | --- |
| A → B 읽기 | `GET /api/entries/6` (A의 토큰) | `404 {"error":"not_found","message":"그런 기록이 없어요."}` |
| A → B 수정 | `PUT /api/entries/6` (A의 토큰) | `404` |
| A → B 삭제 | `DELETE /api/entries/6` (A의 토큰) | `404` |
| **주인이 부르면** | `GET /api/entries/6` (B의 토큰) | `200` — B의 기록 |
| B → A 읽기 | `GET /api/entries/1` (B의 토큰) | `404` |
| B → A 수정 | `PUT /api/entries/1` (B의 토큰) | `404` |
| B → A 삭제 | `DELETE /api/entries/1` (B의 토큰) | `404` |

**403이 아니라 404를 쓴 이유**: 403은 "있긴 한데 너는 안 돼"라고 알려주는 셈이라, 남의 기록 id가 실제로 있다는 사실이 새어 나갑니다. 404는 그것조차 알려주지 않습니다.

**거절 앞뒤로 반대편 자료가 그대로인지**: A가 B를 건드리기 전 B는 **2건**, 건드린 뒤에도 **2건**이었고, 응답 JSON을 통째로 비교해도 **한 글자도 다르지 않았습니다.** 반대 방향도 A가 **5건 → 5건**, 내용 동일. 새로 생긴 기록도 없습니다.

### 확인 4 — 주소 · 헤더 · 본문에 남의 계정을 적어 보내면

| | 요청 (전부 A의 토큰) | 응답 |
| --- | --- | --- |
| 주소 | `GET /api/entries?userId=2` | `200` — 돌아온 기록 id `[1,2,3,4,5]` (**A 것뿐**) |
| 헤더 | `GET /api/entries` + `X-User-Id: 2` | `200` — 돌아온 기록 id `[1,2,3,4,5]` (**A 것뿐**) |
| 본문 | `PUT /api/entries/date/2026-09-06` 본문에 `{"userId":2,"user_id":2,...}` | `200` — **A의** 2026-09-06으로 저장됨. B의 목록에는 그 날짜가 생기지 않음 |

서버는 주소·헤더·본문의 계정 번호를 **읽는 코드 자체가 없습니다.** 계정은 `requireAuth` 가 토큰에서 정한 `req.user.id` 하나뿐입니다.

### 확인 5 — 목록에 남의 자료가 섞이지 않고, 비밀번호가 그대로 보이지 않는다

**목록** — 같은 주소·같은 방식(`GET /api/entries`)에 토큰만 바꿔 불렀습니다.

| 토큰 | 응답에 들어 있는 기록 id |
| --- | --- |
| A | `1, 2, 3, 4, 5` |
| B | `6, 7` |

겹치는 id **0개**. 응답 전체를 열어봐도 남의 계정 기록은 한 건도 없습니다.

**저장된 비밀번호** — `users` 테이블을 그대로 열어본 것입니다. **두 계정은 똑같은 비밀번호로 만들었습니다.**

```text
id=1  email=mochi-a@example.com
password_hash=$2b$12$TaYWqBoF5TXHLWxJHj.2HONopQcwQ6okhZ2XRnudmbjQfbxKBMl8.
id=2  email=mochi-b@example.com
password_hash=$2b$12$WUjpgjt2mZMN5e6wBRVZjOX7x.7xEF2TUnZ7AcwZhP5IsjUWseVO.
```

- 입력한 글자는 어디에도 보이지 않습니다.
- **같은 비밀번호인데 저장된 값이 서로 다릅니다.** bcrypt가 계정마다 다른 소금값을 붙이기 때문입니다(`$2b$12$` 뒤 22글자가 그 계정의 소금값).
- 로그인 요청·응답 기록에도 원문이 없습니다(위 확인 기록의 본문은 전부 `"password": "********"`).
- 서버 로그 53줄 전체를 뒤져도 비밀번호 원문은 **한 건도 없습니다.** 로그에는 시각·방식·경로·상태 코드만 남깁니다(`server.js:184`).

### 곁들여 확인한 것

| 확인 | 결과 |
| --- | --- |
| 같은 이메일로 두 번 가입 | `409 {"error":"email_taken"}` — `email_lower` 에 UNIQUE 제약 |
| 아이디 맞고 비밀번호만 틀림 / 아이디 자체가 없음 | **둘 다 `401` + `"이메일 또는 비밀번호가 올바르지 않아요."`** (문자열까지 동일) |
| 토큰 만료 | 발급 12시간 뒤 `401 session_expired`. `sessions.expires_at` 에 기록 |
| 토큰이 주소에 실리는가 | 아니요. 항상 `Authorization` 헤더 (`app.js:33`) |
| 비밀키가 브라우저 코드·배포 파일·Git에 있는가 | 아니요. `SESSION_SECRET` 은 서버 환경변수뿐. `.env` 는 `.gitignore` 에 있고, 저장소에는 `.env.example` 의 자리표시자만 있습니다 |
| 서버에 저장된 토큰의 모습 | `token_hash=9f1a…생략` — 원문이 아니라 HMAC 값 |
| 계정 삭제 | 계정 C 삭제 후 사용자 행 0개, 주인 없는 일기 행 0개 |

## ⑤ AI와 나

**AI에게 맡긴 일** — 인증 백엔드(`server.js`)의 전체 코드 작성, 6번 `script.js` 를 서버 호출 방식으로 옮기는 작업, 로그인 화면 마크업·CSS, 그리고 **확인 기록을 사람이 손으로 치지 않고 실제 요청을 보내 자동으로 받아 적는 스크립트**를 맡겼습니다. 반응형에서 지표 표의 합계 칸이 잘리던 버그도 AI가 찾아 고쳤습니다.

**내가 직접 판단한 일** — ① 인증 서비스를 쓰지 않고 직접 붙이기로 한 결정(이 과제가 요구하는 "어디를 고쳤나"를 보여줄 수 있어야 해서), ② 남의 자료 요청을 **403이 아니라 404** 로 돌려주기로 한 결정, ③ 6번 백엔드를 고치지 않고 새 폴더로 분리해 6번 제출물을 살려 두기로 한 결정, ④ 5일 실험의 질문·지표·계획 규칙과 3일차 전에 무엇을 바꿀지, ⑤ ⑥번 항목에 무엇을 솔직하게 적을지.

**AI 제안을 따르지 않은 일** — AI는 처음에 **JWT(`jsonwebtoken`)** 로 붙이자고 제안했습니다. 코드가 짧고 서버에 세션 표를 둘 필요가 없다는 이유였습니다. 따르지 않았습니다. JWT는 서명만 맞으면 통과시키기 때문에 **로그아웃해도 만료 전까지 그 토큰이 계속 통하고**, 이 과제의 통과 기준(로그아웃 뒤 같은 값으로 요청하면 거절)을 정직하게 만족시키려면 결국 서버에 취소 목록을 따로 둬야 합니다. 그럴 바에는 처음부터 서버 세션이 단순하다고 판단해 방식을 바꿨습니다.

## ⑥ 아직 못 막은 것

솔직하게 적습니다. 아래는 **지금 막지 못한 것들**입니다.

### 1. 무차별 대입 (가장 큰 구멍)

로그인 요청 횟수에 아무 제한이 없습니다. 같은 이메일에 비밀번호를 초당 수십 번씩 계속 넣어 볼 수 있습니다.

**왜 위험한가**: bcrypt 12회가 한 번 확인에 몇십 밀리초를 쓰게 만들어 속도를 크게 늦추긴 하지만, 짧거나 흔한 비밀번호(`password1234` 같은)라면 시간이 걸려도 결국 뚫립니다. 계정 잠금도 없어서 공격이 시작돼도 본인이 알 방법이 없습니다.
**어떻게 막아야 하나**: IP·계정별 시도 횟수 제한(`express-rate-limit` 등), 여러 번 틀리면 잠깐 잠그기, 실패 알림. 이번에는 시간이 모자라 넣지 못했습니다.

### 2. 비밀번호 재설정이 없다

비밀번호를 잊으면 되찾을 방법이 없습니다. 로그인한 상태에서 바꾸는 것만 됩니다.
**왜 위험한가**: 보안 구멍이라기보다 사용성 문제지만, 급하게 붙이려다 "이메일만 맞으면 바꿔 준다" 같은 위험한 방식으로 만들기 쉬운 지점입니다. 지금은 아예 없다고 적어 둡니다.

### 3. 토큰을 `localStorage` 에 둔다 (XSS에 약하다)

브라우저가 토큰을 `localStorage` 에 저장합니다. 이 페이지에 남의 스크립트를 심을 수 있는 구멍(XSS)이 생기면 그 스크립트가 토큰을 그대로 읽어 갈 수 있습니다.
**왜 위험한가**: 토큰을 훔치면 비밀번호를 몰라도 남의 일기를 다 볼 수 있습니다. 만료가 12시간이라 피해 창이 그만큼 열려 있습니다.
**지금 상태**: 화면에 값을 넣을 때 `innerHTML` 대신 `textContent` 를 쓰도록 정리해서 XSS가 생길 자리를 줄여 두긴 했지만, 이것은 예방이지 방어가 아닙니다. 제대로 하려면 `HttpOnly` 쿠키를 써야 하는데, 화면(GitHub Pages)과 서버(Render)의 주소가 달라 크로스 사이트 쿠키가 막히는 문제가 있어 이번에는 못 했습니다.

> 이와 관련해 2차 검증에서 **로그아웃한 뒤에도 앞사람의 기록이 숨겨진 채로 화면(DOM)에 남아 있는 것**을 찾아내
> `app.js` 의 `showLogin()` 에서 비운 상태로 다시 그리도록 고쳤습니다. 자세한 내용과 고치기 전·후 확인은
> [`증거/테스트 계정 검증 기록.md`](증거/테스트%20계정%20검증%20기록.md) 의 10-5에 있습니다.
> 토큰이 `localStorage` 에 있다는 위 문제 자체는 여전히 남아 있습니다.

### 4. 두 번째 인증 수단(2단계 인증)이 없다

비밀번호 하나만 맞으면 들어옵니다. 비밀번호가 새 나가면 그걸로 끝입니다.

### 5. 접속 기록(감사 로그)이 없다

서버 로그에 "언제 어떤 경로가 몇 번으로 끝났는지"만 남고, **누가 로그인에 실패했는지·성공했는지는 남지 않습니다.**
**왜 위험한가**: 누가 내 계정을 두드리고 있었는지, 언제 뚫렸는지를 나중에 알 수 없습니다. 사고가 나도 확인할 근거가 남지 않습니다.

### 6. 이메일 확인 절차가 없다

남의 이메일 주소로도 가입할 수 있습니다. 지금은 이메일로 무언가를 보내지 않아 당장 피해는 없지만, 나중에 비밀번호 재설정을 붙이면 곧바로 문제가 됩니다.

### 7. 무료 배포의 저장 한계 — 실제로 겪었습니다

Render 무료 플랜은 디스크가 영구 저장이 아닙니다. **서비스가 다시 시작되면 `diary-auth.db` 가 빌드 직후 상태로 돌아가고, 계정과 일기가 함께 사라집니다.** 다시 시작되는 경우는 두 가지입니다 — 코드를 다시 배포할 때, 그리고 **15분 넘게 요청이 없어 잠들었다가 깨어날 때**.

**왜 위험한가**: 사용자가 성실히 쓴 기록이 예고 없이 통째로 없어집니다. 로그인조차 안 됩니다(계정 자체가 없어지므로). 데이터를 맡아 두는 앱으로서는 인증이 뚫리는 것 못지않게 나쁜 상태입니다.

**추측이 아니라 재본 것입니다**: 계정과 5일 기록을 넣은 뒤 서버에 요청을 한 번도 보내지 않고 **20분을 그대로 두었다가** 로그인하니 `401 invalid_credentials` 가 돌아왔습니다. 재배포한 적도, 코드를 바꾼 적도 없습니다. 시각과 요청·응답을 [`증거/배포 서버 검증 기록.md`](증거/배포%20서버%20검증%20기록.md) 의 0-0에 그대로 남겼습니다.

**어떻게 막아야 하나**: 유료 Persistent Disk를 붙이거나, SQLite를 버리고 관리형 데이터베이스(Neon·Supabase의 무료 Postgres 등)로 옮겨야 합니다. 코드에서 SQL을 쓰는 곳이 `server.js` 한 파일에 모여 있어 옮기는 일 자체는 어렵지 않지만, 이번 제출 기한 안에는 하지 못했습니다.

**심사에는 지장이 없습니다**: 가입은 언제든 되므로, 검증 안내서대로 새 계정을 만들어 확인하시는 데에는 문제가 없습니다. 제 5일 기록은 이 문서와 증거 파일에 그대로 남아 있습니다.

## 5일 동안 잠긴 앱을 실제로 써 본 기록

### 1일차에 한 번만 정한 것 (그 뒤로 바꾸지 않음)

| 항목 | 정한 값 |
| --- | --- |
| 답하려는 질문 | **공부를 아침에 시작하면 하루 공부 시간이 늘어날까?** |
| 관찰 지표 | **공부** (습관 기록의 항목 이름) |
| 단위 | **분** |
| 계산 규칙 | 그날 기록 중 `공부` 항목의 값을 **모두 더해** 하루 값으로 본다 |
| 1일차의 계획 규칙 | **저녁을 먹은 뒤에 공부를 시작한다** |

이 다섯 가지는 앱 안의 **🔬 이번 5일의 실험 설정** 에 저장돼 있습니다(`settings` 표, 계정별).

### 값을 다룰 때의 규칙

| 상황 | 어떻게 하나 |
| --- | --- |
| **값이 빠졌을 때** | 0으로 채우지 않습니다. 그 날은 "없음"으로 두고 **평균의 분모에서도 뺍니다.** 0으로 채우면 "안 한 날"과 "적는 걸 잊은 날"이 구분되지 않기 때문입니다. |
| **값이 중복될 때** | 같은 날 `공부` 항목이 여러 줄 있으면 지우지 않고 **모두 더합니다.** 오전·오후로 나눠 적은 것으로 보기 때문입니다. |

| **반올림** | 화면에 보이는 합계·평균은 **소수 셋째 자리에서 반올림**(소수 둘째 자리까지 표시)합니다. 저장되는 원본 값은 반올림하지 않습니다. |
| **주 시작 요일** | **월요일**입니다(월~일). "이번 주 요약"이 이 기준으로 묶입니다. |

### 화면에 보이는 합계·평균을 손으로 더해 맞춰 보기

앱의 **📊 지표 요약**에 이렇게 보입니다:

> 공부 합계 **285분** · 기록한 5일 평균 **57분**
> 규칙 변경 전 2일 평균 **32.5분** → 변경 후 3일 평균 **73.33분** (+40.83분)

손으로 더한 값:

```
합계   40 + 25 + 75 + 90 + 55 = 285      -> 화면 285분   같음
평균   285 / 5 = 57                       -> 화면 57분    같음
변경 전 (40 + 25) / 2 = 32.5              -> 화면 32.5분  같음
변경 후 (75 + 90 + 55) / 3 = 73.333...    -> 화면 73.33분 같음 (소수 셋째 자리에서 반올림)
차이   73.33 - 32.5 = 40.83               -> 화면 +40.83분 같음
```
